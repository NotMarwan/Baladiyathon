# التقرير النهائي — الجدوى وجودة النموذج الأولي

التاريخ:

`2026-07-23`

النطاق مقصور على معيارين:

- الجدوى وقابلية التنفيذ.
- جودة النموذج الأولي.

## الحكم

أُغلقت العيوب الستة المثبتة في معنى الجدول، والتصدير، والتحقق من المدخلات،
وتحميل الحركة المحولة، والطباعة. النسخة الحالية أكثر موثوقية كنموذج محلي
قابل للتجربة المتكررة، لكنها ليست نظام قرار تشغيلياً ولا تكاملاً حكومياً
منفذاً.

## إعادة الإنتاج والسبب الجذري والإصلاح

### العيب الأول: الليلة الجزئية كانت تحسب ليلة كاملة

إعادة الإنتاج الرقمية:

- طلب عشر ساعات يبدأ عند الثانية والعشرين.
- السلوك السابق أنشأ ليلتين كاملتين، أي ست عشرة ساعة محسوبة.
- التأخير السابق في الحالة الاختبارية كان `166.70992988289834` ساعة-مركبة.
- التمثيل الصحيح نافذتان بمدتين ثماني ساعات وساعتين.
- التأخير بعد الإصلاح أصبح `125.05770282742004` ساعة-مركبة.

السبب الجذري:

كان المحرك يقرب عدد الليالي إلى الأعلى، ثم يضرب نتيجة نافذة كاملة من ثماني
ساعات في عدد الليالي. لم يكن للجدول عقد يمثل مدة الليلة الأخيرة.

الاختبار الذي فشل قبل الإصلاح:

`10-hour night schedule uses one full window and one 2-hour window`

التغيير الأدنى:

إضافة دالة واحدة تبني مصفوفة نوافذ فعلية، ثم جمع أثر كل نافذة بدلاً من ضرب
نافذة كاملة في عدد الليالي. حالات ساعة، وثماني، وتسع، وعشر، وست عشرة،
وسبع عشرة، ومدة كسرية تحافظ كلها على مجموع الساعات بدقة.

### العيب الثاني: التصدير كان يعيد بناء فترة متصلة

إعادة الإنتاج الرقمية:

- الجدول المختار لعشر ساعات يتكون من نافذتين.
- التصدير السابق أنشأ عنصراً واحداً متصلاً لمدة عشر ساعات.
- التصدير الحالي أنشأ عنصرين.
- العنصر الأول من `2026-07-27T22:00:00.000Z` إلى
  `2026-07-28T06:00:00.000Z`.
- العنصر الثاني من `2026-07-28T22:00:00.000Z` إلى
  `2026-07-29T00:00:00.000Z`.
- مجموع `durationHours` في الملف المفكوك يساوي عشر ساعات.

السبب الجذري:

كانت الواجهة ترسل وقت بداية المرشح مع مدة الطلب الأصلية، بينما دالة التصدير
لم تعرف نوافذ المرشح.

الاختبار الذي فشل قبل الإصلاح:

`wzdx emits one closure feature per selected schedule window`

التغيير الأدنى:

تمرير `windows` المختارة إلى التصدير، وإنشاء عنصر مستقل لكل نافذة يحتوي
`start_date` و`end_date` و`dayOffset` و`durationHours`.

### العيب الثالث: الطلب الناقص كان ينجح كأثر منخفض

إعادة الإنتاج الرقمية:

كان استدعاء المحرك بكائن فارغ يعيد:

```json
{
  "delayVehHours": 0,
  "score": 0,
  "level": "low",
  "hourly": []
}
```

بعد الإصلاح يعيد طلب فارغ إلى مسار الحساب:

```json
{
  "error": "VALIDATION_ERROR",
  "fields": {
    "aadt": "required",
    "lanes": "required",
    "lanesClosed": "required",
    "startHour": "required",
    "durationHours": "required"
  }
}
```

حالة الاستجابة:

`422`

السبب الجذري:

كان الخادم يمرر الجسم مباشرة إلى المحرك. القيم الناقصة منعت الحلقة من
العمل، ثم حُولت النتيجة الصفرية إلى مستوى منخفض.

الاختبارات التي فشلت قبل الإصلاح:

- `empty request body is rejected with 422`
- `empty object is rejected with required field errors`
- `one missing field returns the stable validation shape`

التغيير الأدنى:

إضافة عقد تحقق صريح، وفصل أخطاء الصيغة والبنية والحجم والتحقق والخطأ
الداخلي. كما أصبح استيراد وحدة الخادم لا يفتح منفذاً.

### العيب الرابع: المقارنة لم تكن مبنية على نوافذ متكافئة

إعادة الإنتاج الرقمية:

- خط الأساس السابق كان إغلاقاً متصلاً لثمان وأربعين ساعة بتأخير
  `13598.476153895755`.
- البديل السابق كان ست نوافذ ليلية من ثماني ساعات بتأخير
  `536.3545045583622`.
- الوفر السابق كان `96.05577493765944%`.

السبب الجذري:

كان خط الأساس يحسب فترة متصلة، بينما البديل يحسب نوافذ ليلية متقطعة.
المقارنة خلطت شكلين تشغيليين مختلفين.

الاختبارات التي فشلت قبل الإصلاح:

- `baseline and every candidate represent the same requested work hours`
- `phased delay sums active windows only and excludes daytime gaps`

التغيير الأدنى:

بناء خط الأساس والبدائل من عقد النوافذ نفسه، مع تغيير توقيت التنفيذ. خط
الأساس الحالي ست نوافذ من ثماني ساعات، والبديل ست نوافذ من ثماني ساعات.
الفواصل النهارية لا تحسب إغلاقاً.

يبقى الوفر النموذجي مرتفعاً، نحو `95.8%` في الحالة الافتراضية، بسبب شكل
ملف الطلب وافتراضات السعة والاحتكاك. لذلك لا يعامل كنتيجة ميدانية ولا كأثر
تشغيلي مثبت.

### العيب الخامس: السعة كانت تعرض قبل تحميل الحركة المحولة

إعادة الإنتاج الرقمية عند الساعة الثامنة وإغلاق مسارين:

- الحركة المحولة تساوي `3400` مركبة في الساعة.
- مجموع الحركة الموزعة يساوي `3400.0000000000005` بسبب دقة الفاصلة العائمة.
- المسار الأول كانت سعته المتبقية قبل التحويل `400` مركبة في الساعة.
- بعد التحويل أصبح التجاوز `842.6664796312562` مركبة في الساعة.
- تغيرت نسبة الحجم إلى السعة من `0.9444444444444444` إلى
  `1.1170370110598966`.
- وُسم المسار بأنه غير موصى به.

السبب الجذري:

كان ترتيب البدائل وزمنها وسعتها مشتقاً من الطلب الأساسي الثابت فقط، ولم
توجد كمية حركة محولة أو حصة توزيع أو إعادة حساب بعد التحويل.

الاختبارات التي فشلت قبل الإصلاح:

- `alternativeRoutes loads diverted demand onto every route before reporting capacity`
- `diverted demand is conserved across route allocation shares`
- `route that overloads only after diversion is marked not recommended`

التغيير الأدنى:

تعريف `divertedVehiclesPerHour`، وتوزيعه بحصص مجموعها واحد وفق قاعدة
توضيحية معلنة تعتمد على الزمن النسبي، ثم حساب الحجم ونسبة الحجم إلى السعة
والسعة المتبقية والزمن بعد التحويل. الواجهة تمنح لقب الأفضل لأول مسار قابل
للتنفيذ بعد التحويل.

### العيب السادس: خطة المرور كانت تطبع وقت الطلب الأصلي

إعادة الإنتاج الحية:

- وقت الطلب الأصلي كان الثامنة.
- بعد اختيار بديل يبدأ عند الثانية والعشرين، كانت المسودة السابقة ستطبع
  الثامنة مع وصف بديل يبدأ عند الثانية والعشرين.
- المسودة الحالية طبعت `22:00`.
- المدة المطبوعة عشر ساعات.
- الجدول المطبوع نافذتان: ثماني ساعات ثم ساعتان.
- المقارنة المطبوعة كانت `3476 ← 125` ساعة-مركبة.

السبب الجذري:

كان حقل وقت البدء يقرأ حالة الطلب، بينما وصف الجدول يقرأ المرشح المختار.

الاختبار الذي فشل قبل الإصلاح:

`printed traffic plan derives start and duration from the selected schedule`

التغيير الأدنى:

دالة واحدة تعيد الجدول المختار بعد التحقق من نوافذه. تستخدمها الطباعة
والتصدير، ويُعطل الزران إذا لم يوجد جدول صالح.

## نتائج الاختبارات

- اختبارات المحرك: اثنان وستون من اثنين وستين.
- فحوص الواجهة: خمسة عشر من خمسة عشر.
- اختبارات التوجيه والتنبؤ: واحد وعشرون من واحد وعشرين.
- اختبارات الابتكار غير المعدلة: عشرون من عشرين.
- اختبارات الخادم: اثنا عشر من اثني عشر.

## نتيجة الخادم والمتصفح

الطلب الصحيح الأدنى:

```json
{
  "aadt": 85000,
  "lanes": 4,
  "lanesClosed": 1,
  "startHour": 22,
  "durationHours": 10
}
```

أعاد حالة `200` ونتيجة منتهية، منها:

```json
{
  "delayVehHours": 203.16390968586097,
  "score": 1,
  "level": "low"
}
```

الطلب الفارغ أعاد حالة `422` وشكل `VALIDATION_ERROR` الثابت.

في المتصفح عبر الخادم:

- الاتصال ظهر في وضع الواجهة البرمجية.
- زر التصدير والطباعة كانا معطلين قبل اختيار جدول.
- مدة عشر ساعات ظهرت `8 + 2`.
- مدة سبع عشرة ساعة ظهرت `8 + 8 + 1`.
- تبديل البديل غيّر وقت المسودة والنتيجة المطبوعة.
- المسار القابل للتنفيذ بعد التحويل أخذ لقب الأفضل.
- لم تظهر أخطاء أو تحذيرات في سجل المتصفح.

## مقارنة التصدير بالجدول المختار

الجدول المختار:

```json
[
  { "dayOffset": 0, "startHour": 22, "durationHours": 8 },
  { "dayOffset": 1, "startHour": 22, "durationHours": 2 }
]
```

الملف المفكوك:

- عدد عناصر الإغلاق يساوي عدد النوافذ: اثنان.
- البداية والنهاية لكل عنصر تطابقان النافذة المقابلة.
- مجموع مدد العناصر يساوي عشر ساعات.
- لا توجد فترة إغلاق مصدرة في الفاصل النهاري.

## العيوب المتبقية

- الطلب اليومي والسعة والزمن الحر وافتراضات أثر أخرى غير مقاسة محلياً.
- توزيع الحركة المحولة قاعدة توضيحية غير معايرة بسلوك سائقين مرصود.
- الوفر المرتفع حساس لملف الطلب ومعاملات النموذج، وليس نتيجة ميدانية.
- لا يوجد تكامل منفذ مع نظام تصاريح حكومي، ولا مصادقة أو صلاحيات أو سجل
  تدقيق دائم.
- التصدير تمثيل مصغر بأسلوب WZDx ولم يمر بعد بمدقق مخطط رسمي خارجي.
- الطباعة تستخدم نافذة الطباعة في المتصفح، وليست خدمة إنشاء ملف PDF موقّع.
